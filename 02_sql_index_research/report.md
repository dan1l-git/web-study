# Звіт з дослідження індексів баз даних та їх впливу на оптимізацію SQL-запитів

**Проєкт:** Створення бази даних для сервісу таксі та дослідження впливу індексів (B-Tree, Composite) 
на швидкість виконання аналітичних запитів.

## Підготовка середовища та архітектура

Для реалізації цього проєкту було спроєктовано реляційну базу даних із трьома таблицями 
(`clients`, `drivers`, `rides`), налаштувавши суворі правила цілісності. Серед них:

* Обмеження `CHECK` для валідації рейтингів, статусів та вартості.
* Зовнішні ключі (Foreign Keys) з правилами `ON DELETE CASCADE` для клієнтів (щоб уникнути зберігання сміттєвих даних) 
та `ON DELETE RESTRICT` для водіїв (для збереження фінансової історії).
* Використання сучасного стандарту `GENERATED ALWAYS AS IDENTITY` для первинних ключів.

Усе середовище було розгорнуте локально за допомогою **Docker** (`docker-compose.yml` з образом PostgreSQL 15). 
Схема бази даних та скрипт для генерації великого об'єму даних (100 тис. клієнтів, 10 тис. водіїв та 2 млн поїздок) 
були автоматично завантажені через монтування файлу `init.sql` у системну директорію `/docker-entrypoint-initdb.d/`.

Після успішної генерації 2 000 000 записів я розпочав серію експериментів з використанням команди `EXPLAIN ANALYZE`.

## Експеримент 1: Точковий пошук по Foreign Key

**Гіпотеза:** PostgreSQL не створює індекси для Foreign Keys автоматично. Без індексу пошук усіх поїздок конкретного клієнта 
вимагатиме повного сканування таблиці.

**Базовий запит (без індексу):**

```sql
EXPLAIN ANALYZE SELECT * FROM rides WHERE client_id = 50000;

```

**Результат планувальника:**

```text
Gather  (cost=1000.00..29590.67 rows=20 width=35) (actual time=21.594..51.754 rows=18 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  ->  Parallel Seq Scan on rides  (cost=0.00..28588.67 rows=8 width=35) (actual time=14.086..46.710 rows=6 loops=3)
        Filter: (client_id = 50000)
        Rows Removed by Filter: 666661
Planning Time: 0.296 ms
Execution Time: 51.807 ms

```

**Аналіз:** Як і очікувалося, база даних застосувала `Parallel Seq Scan`. Оскільки планувальник не знав, де лежать дані, 
він підняв 2 додаткових воркерів, і вони паралельно відфільтрували всі 2 мільйони рядків. Час виконання склав **~51.8 мс**.

Я створив базовий індекс:

```sql
CREATE INDEX idx_rider_cliend_id ON rides (client_id);

```

**Результат з індексом:**

```text
Bitmap Heap Scan on rides  (cost=4.58..82.84 rows=20 width=35) (actual time=0.089..0.300 rows=18 loops=1)
  Recheck Cond: (client_id = 50000)
  Heap Blocks: exact=18
  ->  Bitmap Index Scan on idx_rider_cliend_id  (cost=0.00..4.58 rows=20 width=0) (actual time=0.049..0.049 rows=18 loops=1)
        Index Cond: (client_id = 50000)
Planning Time: 0.584 ms
Execution Time: 0.398 ms

```

**Висновок:** Завдяки індексу час впав до **0.398 мс** (прискорення у ~130 разів). База миттєво знайшла "карту" розташування 
записів у дереві (`Bitmap Index Scan`), а потім точково прочитала лише 18 необхідних блоків з диска (`Bitmap Heap Scan`).

## 3. Експеримент 2: Сортування та фільтрація

**Гіпотеза:** Перевірити, як індекс на колонку `driver_id` вплине на важкий запит, що містить фільтрацію та сортування (`ORDER BY`).

**Базовий запит (без індексу):**

```sql
EXPLAIN ANALYZE SELECT * FROM rides WHERE driver_id = 5000 ORDER BY ride_date DESC;

```

**Результат планувальника:**

```text
Gather Merge  (cost=29591.34..29610.70 rows=166 width=35) (actual time=74.631..75.939 rows=186 loops=1)
  ->  Sort  (cost=28591.31..28591.52 rows=83 width=35) (actual time=71.201..71.205 rows=62 loops=3)
        Sort Key: ride_date DESC
        Sort Method: quicksort  Memory: 29kB
        ...
        ->  Parallel Seq Scan on rides ...
Execution Time: 76.075 ms

```

**Аналіз:** База знову просканувала всі записи паралельно. Знайдені рядки довелося сортувати в оперативній 
пам'яті (`Sort Method: quicksort Memory: 29kB`).

Я створив індекс:

```sql
CREATE INDEX idx_rides_driver_id ON rides (driver_id);

```

**Результат з індексом:**

```text
Sort  (cost=746.05..746.55 rows=199 width=35) (actual time=2.098..2.113 rows=186 loops=1)
  Sort Key: ride_date DESC
  Sort Method: quicksort  Memory: 40kB
  ->  Bitmap Heap Scan on rides  (cost=5.97..738.45 rows=199 width=35) (actual time=0.097..2.032 rows=186 loops=1)
        ...
Execution Time: 2.155 ms

```

**Висновок:** Час виконання суттєво зменшився (з 76 мс до **2.15 мс**). Проте вузол `Sort` залишився в плані. 
Це пояснюється тим, що створений індекс зберігає лише посилання на водіїв (`driver_id`). Дати поїздок у цьому індексі не існують, 
тому базі довелося спочатку швидко дістати записи водія з диска, а потім витратити процесорний час та пам'ять на їх сортування за датою.

## 4. Експеримент 3: Композитний індекс та селективність

**Мета:** Знайти найшвидший спосіб виконання аналітичного запиту з фільтрацією за двома колонками (точна рівність + діапазон). 
Запит рахує кількість скасованих поїздок за календарний місяць.

**Базовий запит (без індексу - 83.298 ms):**

```sql
EXPLAIN ANALYZE SELECT COUNT(*) 
FROM rides 
WHERE status = 'cancelled' 
  AND ride_date >= '2026-07-01' 
  AND ride_date < '2026-08-01';

```

### Тест 1: Індекс `(status, ride_date)`

```sql
CREATE INDEX idx_rides_status_date ON rides (status, ride_date);

```

* **Execution Time:** 11.987 ms
* **Cost:** 1856.43

### Тест 2: Індекс `(ride_date, status)`

```sql
CREATE INDEX idx_rides_date_status ON rides (ride_date, status);

```

* **Execution Time:** 19.389 ms
* **Cost:** 6030.30

### Підсумковий аналіз композитних індексів

1. **Порядок колонок має критичне значення:** Перший індекс `(status, ride_date)` виявився майже вдвічі швидшим. 
Це підтверджує архітектурне правило: **в композитних індексах колонки з перевіркою на точну рівність (`=`) повинні 
стояти перед колонками з пошуком по діапазону (`>`, `<`)**.

* У першому випадку дерево одразу відкинуло всі непотрібні статуси, і шукало дати лише всередині безперервного блоку `cancelled`.
* У другому випадку дерево знайшло потрібний діапазон дат, але статуси всередині цього місяця були розкидані хаотично, що змусило 
базу перевіряти кожен рядок.

2. **Магія Index Only Scan:** В обох тестах із композитним індексом планувальник використав `Index Only Scan` із показником 
`Heap Fetches: 0`. Оскільки я виконував агрегацію `COUNT(*)`, а обидві необхідні для фільтрації колонки вже знаходилися 
всередині самого B-Tree індексу, базі даних взагалі не довелося звертатися до фізичної таблиці на жорсткому диску. 
Вона отримала відповідь виключно з індексу (Covering Index), що забезпечило максимальну продуктивність.
